# TIU BSS code fixes — 28 October 2026

This update is based on the published Sites source `49d3cf4597af8ef27271c094b42613bcfd14f0ba` and preserves its Firebase Authentication plus Sites D1/R2 architecture. Firebase billing remains Spark. This pass changes source code only; it does not deploy, change cloud settings, grant roles, or modify member records.

## Current website fixes

- Private API requests recheck the initiating account after obtaining its token and before sending a draft. An account switch or signout prevents the request from reaching the server. Signed-out private requests fail before network access; the independent Admin session remains supported.
- Firebase auth callbacks ignore stale success and failure results after an account or token revision changes.
- Signout, account switches and privilege changes clear private forms and dialogs immediately. Background updates for the same account preserve unsaved edits.
- Suspended, rejected or missing-profile staff cannot read delegated registrations, pickup tokens or order records. Their own records remain available, and independent Admin access remains intact.
- Community-request retries preserve the saved response for identical normalized input. Conflicting content or recipients under the same request ID return HTTP 409 instead of silently discarding changes. Legacy records remain compatible.

The old Firestore 100-ticket limit is obsolete in the current native API, which returns the complete authorized registration list. No Firestore adapter was restored.

## Retained optional Firebase backend

The optional Functions source now requires a saved named profile before event registration, blocks self/super-admin role replacement through the staff form, and validates community-request retries. These changes do not add membership-approval or email-verification requirements for saved legacy profiles.

Its preflight resolves existing Windows Firebase CLI JavaScript entrypoints without a shell and reports the configured App Check provider. Documentation clearly distinguishes this optional deployment from the current website, which does not require Firebase Functions or Storage.

## Follow-up fixes

The follow-up addresses all seven bugs found in the subsequent audit of commit `60cef18`:

- Google sign-in uses the returned credential, and the adapter publishes the confirmed account before its staff-role request finishes. Logout and newer-account results still take precedence.
- Sent-request history, counts, and account exports recognize the native `uid` owner field while retaining compatibility with older records and excluding other members' records.
- Connection and mentorship forms retain the same request key after a lost response and block concurrent submissions. A message edit starts a new request. An explicit submission marker keeps retries separate from admin status updates, including legacy records already loaded in the dashboard.
- New community requests have server-generated record IDs separate from their per-member retry keys, so two senders using one client key cannot cause moderation to change the wrong record. Existing ambiguous legacy IDs fail with HTTP 409 without modifying either record; existing nonambiguous legacy retries continue to work.
- Event registrations retain accepted request keys, including aliases from another tab. Retrying a cancelled registration returns its cancelled ticket and preserves free capacity; a new key permits deliberate rebooking. The UI reports a cancelled result accurately.
- Event slug uniqueness is checked inside each atomic database write, covering concurrent creation and renaming without a new database migration.
- Public and admin content reads always include saved builtin overrides independently of the 1,000-custom-record cutoff. Hidden builtin content stays hidden and remains editable.

Final review additionally found and closed an account-switch timing gap while staff roles load. Account changes clear the previous identity and roles before asynchronous work, and fallback role refreshes cannot publish a stale account or its roles.

These are source-only changes for GitHub. They do not activate a production deployment or change the Firebase Spark plan. Existing ambiguous legacy request IDs, if any, require a separate data repair; the code prevents incorrect moderation and prevents new collisions.
